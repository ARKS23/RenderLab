### 4.1 工程组织

以现有 RenderLab 为基础继续开发，不重新创建工程。下列结构区分已有目录与后续建议；保留已有地图和源码组织，不为了匹配示例批量迁移资产。

旧示例中的 `RenderExperiments` 统一对应现有 `RenderLabRendering`；不创建第二个渲染插件。年度路线和项目路线均保留在 `Docs/`，不另建第三份总计划。

先固定 UE 5.8 的具体版本、一个 RHI 和一套测试配置。第三方仓库记录分支与提交号。不要一边学算法一边频繁升级引擎。

建议先使用普通不透明网格、固定曝光和固定分辨率，单独记录 Lumen、Nanite、硬件光追、抗锯齿和屏幕百分比设置。先控制变量，再测试复杂组合。

### 4.2 从最小 Pass 到传统算法

**顺序：**

1. **Lab03 收尾：**沿用可调灰度／通道变换成果，补齐抓帧、生命周期与首次打包。
2. **Lab04A：**最小横向模糊、纵向模糊与合成，理解中间纹理和多 Pass 依赖。
3. **Lab04B：**在插件中单独显示深度、法线和重建位置，确认含义、空间及有效区域。
4. **Lab04C：**实现 AO，先看独立灰度结果，不急着修改完整光照流程。
5. **Lab04D：**加入深度／法线引导滤波，比较低采样原始结果、滤波结果和高采样参考。
6. **Lab04E：**多场景、性能与边界测试、打包回归和作品展示，形成 V1。
7. 有余力再做半分辨率上采样或基础时域处理，选一项；Compute Shader 按一个受控实验引入，不先重写全部 Pass。

子任务的进入条件与验收统一见[项目路线 Lab04](UE_Rendering_Learning_Roadmap.md#lab04)。这是原多 Pass 练习的延伸，不再单独安排一套模糊项目。Lab05 保留给 Mesh，Lab06 保留给后续性能深化。

RDG 表达 Pass 与资源依赖；SceneViewExtension 提供接入位置；Global Shader 是编写自定义着色器的一种方式。这些概念围绕同一个实验学习。主资料：[R03]、[R04]；小型接入参考：[R23]。

不要把 LearnOpenGL 的坐标转换直接原样搬到 UE。先验证当前路径使用的投影、深度、法线编码和视图区域，再实现算法。后处理输入和屏幕坐标问题参考 [R02]，算法原理参考 [R19]。

### 4.3 实现时必须说清楚的事项

| 事项 | 自查问题 |
|---|---|
| 输入 | 深度是什么表示？法线在哪个空间？背景像素怎么处理？ |
| 尺寸 | ViewRect 与纹理尺寸是否一致？缩放、窗口变化后还正确吗？ |
| 计算 | 为什么这样采样？半径是什么单位？哪些情况下会漏掉信息？ |
| 输出 | 输出被谁消费？独立 AO 展示与正式接入光照分别做到哪一步？ |
| 线程 | 谁更新参数？渲染端读到的数据由谁持有？ |
| 生命周期 | PIE 重启、关卡切换、目标销毁时怎样处理？ |
| 性能 | 慢在采样、带宽、分辨率、额外 Pass，还是 CPU 提交？ |

渲染线程的数据所有权参考 [R05]。RDG 临时资源不能当作永久对象保存；需要跨帧时，按外部资源与提取机制设计生命周期。[R04]

### 4.4 基础时域实验：可选，但值得在专项前理解

先限制为静态几何和移动相机：

1. 找到当前像素的历史位置，验证坐标与抖动处理。
2. 读取历史结果，做最简单积累。
3. 检查越界、深度不一致与遮挡解除，拒绝不可信历史。
4. 相机切换、分辨率变化时重置历史。
5. 再决定是否加入移动物体和速度缓冲。

分别保存静止、平移、快速旋转、遮挡解除四段短视频。先观察失败，再加修正。不要仅凭静态截图宣称时域稳定。

先看 GAMES202 的 backprojection、motion vector、temporal accumulation 与去噪内容 [R20]；再按问题阅读 UE TSR 文档 [R17]。这里是理解时域问题，不要求复刻整个 TSR。

### 4.5 比较什么，怎样测量

至少保留三组：

| 方案 | 作用 |
|---|---|
| 低采样原始 AO | 输入质量与开销 |
| 低采样 AO + 引导滤波 | 有实际意义的传统对照 |
| 同一方法的高采样 AO | 质量参考，明确其采样方式和限制 |

高采样 SSAO 仍是屏幕空间近似，不等同于真实几何 AO；也不要仅凭“32 samples”就称为 Ground Truth。需要更严格参考时，再研究带光追参考的实现，例如 XeGTAO。[R19]、[R25]

建议测量流程：

- 固定场景、相机、分辨率、画质、抗锯齿、屏幕百分比和帧率限制。
- 笔记本固定供电与性能模式，记录温度／频率明显变化。
- 等待 Shader 编译与资源加载稳定，再进行多次采样。
- 记录毫秒、样本量、平均值和波动；不要只报告 FPS。
- 区分最终 AO Pass、额外处理和整帧成本。
- 抓帧用于定位输入输出；最终性能在正常运行中重复测量。

工具学习顺序：`stat unit` 等基础观察 → RenderDoc 抓帧 → Unreal Insights 时间线。相关入口：[R06]、[R07]、[R08]。

## 5. 神经渲染专项：两条路线只选一条

### 5.1 共同起点：最小训练实验

预计先用 2–3 周中的部分项目时间完成，不另外开启一整套长期 AI 课程。

1. 用小型 MLP 拟合简单标量函数，观察训练、验证和过拟合。
2. 改为 `(u, v) → RGB` 图像函数拟合。
3. 比较网络宽度、层数，以及一种输入编码。
4. 保存权重与配置，从新进程加载并生成结果。
5. 为未来部署导出一个微型模型，检查输入尺寸与运算支持。

必须理解：Tensor 形状、梯度、训练／推理状态、Loss、学习率、数据划分与随机种子。主资料：[R21]。完成基础版后可参考 tiny-cuda-nn 的图像拟合示例，初期不要求读懂其 CUDA 内核。[R26]

**边界：**单图拟合主要证明函数表示和优化能力，不能据此宣称学会了跨场景 GI 或拥有泛化能力。

### 5.2 分支 A：图像重建／去噪

适合后续题目偏画面增强、低采样重建、去噪等方向时选择。

```text
低质量 AO + 深度 + 法线
            ↓
      小型残差 CNN
            ↓
       重建 AO
```

建议先用数层卷积完成可训练版本；U-Net 是后续对照，不是起步门槛。

**动手顺序：**

1. 给少量普通图像加噪声，仅用于熟悉训练流程。
2. 从 UE 导出真正的低质量输入与高采样参考。
3. 可视化输入、目标和差值，确认数据对齐。
4. 先过拟合极小样本，检查训练过程能否正常工作。
5. 再扩大数据，训练、验证、测试按场景或独立镜头划分。
6. 比较传统引导滤波、简单 CNN 和一个改进设置。
7. 通过离线评估后，再投入实时接入。

**数据约定至少记录：**帧与相机标识、分辨率、深度表示、法线空间、AO 定义、采样数、随机种子、抖动／曝光／后处理设置。数据和标签用合适的数值格式保存，不拿有损截图替代原始缓冲。

**最低实验：**

- 输入只有 AO，对比加入深度／法线。
- 小网络，对比稍大网络。
- 至少一个没有用于训练和调参的场景。
- 相同运动路径下比较闪烁、细节和拖影。
- 不只看 PSNR／SSIM；明确数值范围、参考生成方法和视觉失败。

专题阅读按顺序：GAMES202 去噪部分 [R20] → SVGF 传统方法 [R28] → Recurrent Denoising Autoencoder [R29]。先理解输入、积累、滤波和测试设计，再决定实现哪些部分。

### 5.3 分支 B：神经光照表示／Neural GI

适合题目偏光照压缩、神经缓存、实时查询或小网络 GPU 推理时选择。

**由浅入深：**

1. 小 MLP 表示一张静态光照数据图。
2. 比较纹理存储与网络表示的质量、存储和查询成本。
3. 定义一个受限的静态场景查询问题，例如给定表面位置／法线查询已知照明下的数据。
4. 分析输入是否足够描述目标；改变光照、几何或观察条件后，模型是否仍适用？
5. 根据课题需求，再考虑更完整的采样、更新或 GI 系统。

纹理基线应采用与任务相关的分辨率、格式和采样方式；统计网络权重之外的编码表、中间缓冲等成本。不要只比较权重文件与未压缩图片大小。

建议先读 tiny-cuda-nn 的示例 [R26]；具备基础后读 Neural Radiance Caching [R27]，理解它如何与路径追踪过程结合。

**命名要准确：**静态光照图的神经表示、离线辐照度缓存、动态 GI 是不同范围。做到了哪一层就展示哪一层，暂不把一个坐标 MLP 称为完整 Neural GI。

### 5.4 GPU 接入：在投入大量训练前做兼容性试验

推荐验证路径：

```text
PyTorch 正确结果
      ↓
导出与独立推理的数值对比
      ↓
UE 中的最小模型执行
      ↓
适合目标任务的 GPU 接入
      ↓
完整质量和性能评估
```

ONNX 导出参考 [R22]。NNE 文档当前标为 Beta；CPU、GPU 与 RDG 是不同使用接口，而不是必须全部走一遍的难度等级。普通 GPU 接口提供 CPU 输入输出并发生传输；RDG 接口以 RDG Buffer 接入渲染图。模型导入成功也不保证指定 Runtime 能运行。[R18]

项目初期就确认：目标 Runtime、设备、模型运算、固定／动态尺寸、数据布局、精度及打包条件。

实时方案统计整个路径：

```text
场景资源 → 输入整理 → 推理 → 输出整理 → 后续合成
```

避免把 Python 前向时间直接写成 UE 增加的 GPU 帧时间。避免 CPU 回读不等于不存在纹理／张量转换。先比较 FP32 正确性，再评价低精度的误差与开销。

如果框架接口阻塞，保留离线实验和传统渲染版本。小 MLP 可把固定权重的 Shader 推理作为独立练习，但不预设它比专门 Runtime 更快，也不立即加入 CUDA／图形 API 互操作。

### 5.5 神经专项验收

- [ ] 数据生成、训练、评估和导出有明确命令或步骤。
- [ ] 有传统／简单基线，实验条件一致。
- [ ] 测试划分符合任务目标，避免训练信息泄漏。
- [ ] 保存配置、版本、权重与可复现结果。
- [ ] 有质量、成本和失败分析。
- [ ] 已部署和未部署的部分区分清楚。
- [ ] 明确个人贡献，网络没有胜出时如实分析。

## 7. 引擎源码与性能专题

### 7.1 源码从实际问题进入

2026 年先查当前功能涉及的代码；2027 年 5—6 月再安排集中源码调试。需要内部改动时可提前。

集中阶段保留[Lab05 最小自定义 Primitive Component 实践](UE_Rendering_Learning_Roadmap.md#lab05)，不仅阅读 Mesh 调用链；[Lab06](UE_Rendering_Learning_Roadmap.md#lab06)用于性能深化。当前效果的抓帧、测量和打包随 Lab03/04 完成，不等到这个阶段。

两条阅读线：

1. **一帧如何组织：**从 `FDeferredShadingSceneRenderer::Render` 与 GPU 事件名称找对应 C++ 实现。[R08]
2. **一个普通网格如何提交：**追踪场景代理、`FMeshBatch`、`FMeshPassProcessor`、`FMeshDrawCommand` 与 RHI 提交。[R09]

第二条先选非 Nanite 静态网格，不把它当作所有几何渲染路径的统一说明。

每次阅读只解决一个问题，例如：“这个网格为什么进入这个 Pass？”“这份资源为什么跨帧存在？”“这个参数在哪一侧更新？”

输出只需一页：入口、关键对象、线程、数据所有权、调用关系、验证方法。不要维护几十页没有实际运行验证的调用栈抄录。

### 7.2 何时编译源码版

当需要修改内部实现或调试被现有构建限制的路径时，按官方构建步骤准备对应版本。[R10]

目前约 300GB 可用空间不预先视为一定够用。先清点源码、依赖、构建输出、缓存和数据集；保留可恢复的工程版本。初期无需因为计划而立即购买硬件。

源码练习建议选一个小改动：给特定对象增加调试标识、观察绘制参数变化，或修改一个受控分支。保留原行为对照与可回退提交。

### 7.3 性能专题只选一个做深

| 专题 | 可执行实验 |
|---|---|
| GPU 采样与带宽 | 改变采样数、分辨率和中间资源，观察收益与损失 |
| 神经推理接入 | 分离输入转换、推理、输出转换与合成成本 |
| CPU 任务 | 纯数据计算由主线程改为任务，检查依赖和总耗时 |
| 资源加载 | 比较同步与异步路径，观察首次使用和内存变化 |

任务系统查 [R16]，分析工具查 [R07]。每个实验都先有串行或简单正确基线，再谈并行和优化。

**阶段验收：**一个源码调试案例 + 一个完整优化案例。结果可以是“该优化不值得”，但必须有证据。

## 8. 基础能力怎样穿插学习

### 8.1 C++：把“熟悉”变成可验证能力

每两周结合项目练一个主题，不从语法课重新开始：

| 主题 | 实践方式 |
|---|---|
| RAII／生命周期 | 为资源句柄定义所有权，解释创建、移动、销毁顺序 |
| 容器与失效 | 构造一次迭代器／引用失效，定位并修复 |
| 编译链接 | 独立模块，解释 Public／Private 依赖与链接错误 |
| 并发 | 纯数据后台计算，处理结果回传与对象失效 |
| 内存与缓存 | 做小型布局对比，正确控制变量并解释结果 |
| UObject 与普通 C++ 对象 | 比较 GC 管理与 RAII，选择合适的对象指针类型 |

UE 对象与指针参考 [R12]、[R13]。不要把标准智能指针规则直接无区别套到 UObject 上。

### 8.2 图形学：按问题恢复

- 第一轮：变换、投影、深度、法线、采样、PBR、阴影。
- 做 AO／滤波时：采样分布、空间邻域、屏幕空间缺失信息。
- 做时域时：重投影、抖动、遮挡解除、历史可信度。
- 做 Neural GI 时：渲染方程、辐射度量、蒙特卡洛估计、偏差与方差。

用 GAMES202 [R20]、LearnOpenGL [R19] 和《Real-Time Rendering》[B01] 查对应主题。每次先试着讲解或实现，再决定补哪部分。

### 8.3 操作系统与网络：用三个实验补实践

1. 后台纯数据任务：解释线程、依赖、等待与生命周期。
2. 资源异步加载：观察加载、对象创建、驻留和释放。
3. 双人交互：观察延迟、消息和权威状态。

概念缺口查《Operating Systems: Three Easy Pieces》的相关章节 [B04]；不同时开启操作系统大课全套作业。

### 8.4 算法：维持与检验

先做一次限时自测，确认目前手感。随后每周约 1 小时维持，复盘边界、复杂度、代码完整性和表达。

临近实际笔试时按题型调整。现阶段不追求新增题量。

### 8.5 英文与论文

每周 2 次，每次约 30–45 分钟，计入阅读时间：

1. 带一个具体问题打开官方文档或论文。
2. 先读图、伪代码、输入输出与实验设置。
3. 保留关键术语和 API 原文，必要时借助翻译。
4. 用中文写 5–10 句：问题、方法、条件、结果、疑问。
5. 把其中一个结论落实为实验或代码检查。

论文按“三遍”读：第一遍判断相关性；第二遍画方法与数据流；第三遍只精读准备实现的部分。

求职项目的 Transformer 学习按专题需要展开；Video QA 科研需要的模型知识正常学习，不受本路线起步顺序限制。

### 8.6 使用 AI 与开源代码

- 可以用 AI 解释接口、提出排错假设、检查代码和设计测试。
- 提交前必须能解释关键代码，自己验证运行结果。
- 参考模板后，尝试从空模块重做最小功能，再加入自己的改动。
- 保存引用、许可证和个人贡献说明。
- 不把 AI 给出的性能数字、旧 API 或“可编译”判断当作验证。

## 9. 每周执行方法与缩减方案

### 9.1 常规周：20 小时

| 工作 | 时间 |
|---|---:|
| 当前主项目／课题 | 10 小时 |
| C++／系统／图形基础实验 | 2 小时 |
| 源码、英文与专题阅读 | 2 小时 |
| 算法维持、记录、面试／申请 | 2 小时 |
| 调试返工与科研波动缓冲 | 4 小时 |

当前主项目包括所处阶段的 AI 或客户端任务，不额外叠加。记录和小测可以分散进行，代码开发尽量保留连续的 2–3 小时。

- **忙碌周 8–12 小时：**只承诺一个小交付，暂停新专题。
- **充裕周 25–30 小时：**补数据、测试、源码理解，优先消化缓冲；不自动开启新项目。
- **进入课题或实习：**用实际任务替换对应时段，同时重新估计个人项目容量。

### 9.2 一次学习的固定流程

```text
提出一个问题 → 做最小实验 → 检查输出 → 修改一个条件
           → 记录证据 → 不看教程复述 → 保存可恢复版本
```

例如：“模糊为什么越过几何边缘？”

先显示深度／法线，再只改引导权重，观察边缘和时间变化。避免一次同时修改算法、资源格式、分辨率和网络结构。

### 9.3 防遗忘

每个实验保留：运行步骤、三个概念、一处自己的改动、一张结果或一组测量。

建议在完成后的第 1 周、第 1 个月各做一次短复查：先解释，再改一个参数或边界情况。忘记 API 名称可以查；反复说不清输入输出时要回到实验。

### 9.4 每两周检查

- 有没有可运行的新成果？
- 能否独立解释关键代码？
- 是否验证过一个失败情况？
- 下一周期只解决哪个问题？

连续两个周期延期：删减功能。第一版优先删复杂场景、更多效果和高级时域；再延后神经部署。保留正确性、可复现工程、性能记录和讲解。

卡住约两个学习时段仍无进展：做最小复现，记录假设与证据，查同版本源码或寻求评审。不要反复整段复制模板试错。

## 11. 申请、实习与秋招准备

### 11.1 今年课题公布后怎样调整

在一周内完成筛选：

1. 任务属于传统实时渲染、图像重建、神经表示还是 GPU 推理？
2. 需要的引擎和工具，与你现有成果重合多少？
3. 最重要的前置能力是否已有证据？缺口能否用短实验验证？
4. 时间、固定会议和成果要求是否适合科研安排？

选择一个主方向、一个相近备选。随后用已有工程做 2–3 周定向补强，不重新启动一整套基础路线。

远程课题、科研合作与正式实习按实际性质区分。参与条件未落实前，全年计划继续保留可独立执行的路径；正式承诺投入时，以可持续时间为准。

### 11.2 申请用的五件材料

- 一页简历，个人贡献具体。
- 可复现工程，注明引擎／依赖／硬件／提交版本。
- 两分钟视频，包含对比与失败情况。
- 短技术报告，说明问题、方法、验证、取舍。
- 针对课题的一页准备说明：已有基础、读过的资料、拟做实验与时间。

### 11.3 两版简历的不同重点

| 图形／引擎版 | UE 客户端版 |
|---|---|
| RenderLab、Shader／RDG、源码、GPU 分析、神经实验 | 网易 UI 经历、华为工程经历、ClientLab、资源与网络 |
| 强调算法、数据流、性能与边界 | 强调状态、模块、生命周期和交付 |

过去工作按实际语言与职责描述。Huawei 的 Python 自动化和网易的 Python／UMG 不扩大为 C++ 引擎开发经历，也不因语言不同就省略真实工程贡献。

### 11.4 面试训练

每个项目准备三种长度：

- **2 分钟：**问题、个人贡献、结果。
- **10 分钟：**架构、关键实现、主要取舍。
- **深入追问：**代码、失败、测量方法和改进空间。

常见自测：

1. 如果移除某个输入／Pass，会发生什么？为什么？
2. 哪部分来自参考实现，哪部分是自己的设计？
3. 优化前的瓶颈证据是什么？
4. 为什么用这个资源格式、分辨率、网络规模？
5. 另一个人能否按 README 复现？
6. 如果重新做，你会先改变什么？

建议 V1 完成后找一次代码评审；2027 年 6 月起定期模拟面试。按反馈校准方向，不用给自己虚构录取概率。

## 13. 第一周清单与年度验收

### 第一周历史清单

保留为最初的准备清单，不是 2026-09-30 的当前待办，也不据此要求重做工程与插件。实际状态见[项目进度](UE_Rendering_Learning_Roadmap.md#current-progress)，本次不自动勾选缺少证据的验收项。

- [ ] 记录当前 UE 完整版本、硬件与可用空间。
- [ ] 创建或整理 RenderLab，建立 Git 基线。
- [ ] 跑通 C++ 插件正常构建，不只依赖编辑器热更新。
- [ ] 原样输出，再实现一个可调颜色变换。
- [ ] 恢复深度／坐标变换知识，记录当前尚不清楚的地方。
- [ ] 保存第一份实验记录，下一周从它继续。

若插件／Shader 配置耗时超出预期，先完成最小可运行链路，深度和 AO 顺延。第一周不同时启动训练、源码全量构建与新 Vulkan 工程。

### 年度验收

- [ ] 能独立开发、调试和测量一个 UE 渲染功能。
- [ ] 有一个传统图形算法的完整实现与对照。
- [ ] 有一个可信的神经渲染实验，范围与局限清楚。
- [ ] 能解释自己的 GPU Pass、线程与资源生命周期。
- [ ] 有一个源码调试案例和一个性能分析案例。
- [ ] 有 UE C++ 客户端的资源、状态与网络实践。
- [ ] 工程、视频、报告、简历能够相互印证。
- [ ] 能如实区分个人实现、参考代码、科研和商业经历。
